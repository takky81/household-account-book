# 家計簿アプリ 仕様書

本書は、決定表で表せないもの（システム構成・データモデル・データ形式・算出ルール）だけを扱う。
機能の振る舞いは決定表を正とする（`spec/tables/*.jsonl` / §7）。

---

## 1. 概要

日々の収入と支出を記録し、月ごとに集計して予算と突き合わせる家計簿アプリ。

- 決まった数人が使う。誰と共有するかは取引ごとに決める。カテゴリは全員共通の名前なので、
  同じ「食費」に夫婦の支出と個人の支出が並ぶ
- カテゴリは2段まで分けられる。「食費 / 外食」のように細かく記録しても、集計と予算は
  「食費」でまとめて見られる。小分類は任意で、大分類のまま記録してよい
- 家賃や光熱費のように分担する支出は、支払った人と負担する人を分けて記録する
- 口座・残高・立替の精算は扱わない。1件の収支そのものを記録の単位とする
- 集計は「誰がいくら負担したか」と「誰がいくら払ったか」のどちらでも見られる
- 予算はカテゴリごとに月単位で置く
- 家賃のように毎月同じ額の支出は、定期登録ルールとして置いておくと自動で取引になる
- 取引を CSV で取り込み、各種データを CSV に書き出せる

### 1.1 用語

| 用語 | 定義 |
| --- | --- |
| 取引 | 1件の収入または支出。家計簿の記録単位 |
| 収支区分 | 取引が収入か支出かの別 |
| カテゴリ | 取引の分類。**全ユーザー共通のマスタ**で、収支区分に属する（共有範囲は持たない）。親を持たない「大分類」と、その下に置く「小分類」からなる |
| 大分類 | 親を持たないカテゴリ。取引・予算・集計の既定の単位 |
| 小分類 | 大分類の下に置くカテゴリ。収支区分は親から引き継ぐ。小分類の下にさらに分類は置けない |
| 共有グループ | 取引を共有する相手の集合。メンバーごとに既定の負担割合を持つ |
| 共有範囲 | その記録を共有する相手。共有グループ、または個人。**取引・予算・定期登録ルールが持つ**。個人の共有範囲のメンバーは本人1人だけ |
| 支払者 | 実際にお金を出した人。共用の財布から出したときは「共用」 |
| 負担 | その取引の金額を誰がいくら受け持つか。合計は取引の金額に一致する |
| 負担割合 | 負担を自動で按分するときの重み |
| 対象範囲 | 集計の対象とする共有範囲の集合 |
| 集計基準 | 集計を負担額で見るか支払額で見るかの別 |
| 対象の利用者 | 集計で額を数える相手。対象範囲がグループならそのメンバー全員、それ以外は自分（§5.4） |
| 対象月 | 集計・予算の単位となる月。取引日の年月で決まる |
| 予算 | ある対象月・あるカテゴリに対する支出の上限額 |
| 消化率 | 予算に対する実績の割合 |
| 定期登録ルール | 毎月同じ日に同じ額の取引を作るための雛形。カテゴリ・金額・支払日・支払者・負担を持つ |
| 予定日 | 定期登録ルールがその対象月に取引を作る日。ルールの支払日がその月に無ければ月末日 |

## 2. システム構成

### 2.1 技術スタック

| 領域 | 採用 |
| --- | --- |
| フロントエンド | React + Vite (TypeScript) |
| ホスティング | GitHub Pages |
| バックエンド / DB | Supabase (PostgreSQL) |
| 認証 | Supabase Auth（メールアドレス + パスワード） |
| CSS / UI | Tailwind CSS + shadcn/ui |
| グラフ | 自前の SVG コンポーネント（描画ライブラリを追加しない） |
| CSV 入出力 | 自前のパーサ / シリアライザ（`src/lib/csv.ts`） |
| ユニットテスト | Vitest |
| E2Eテスト | Playwright |
| 決定表の生成スクリプト | Node (TypeScript) |

### 2.2 配信

- GitHub Pages は静的配信のみのため、サーバーサイドのコードを持たない
- データアクセスはブラウザから Supabase へ直接行う
- サブパス配信になるため、Vite の `base` とルータの `basename` を合わせる（`/household-account-book/`）

### 2.3 認証とアクセス制御

- Supabase Auth のメールアドレス + パスワード認証を使う。メールアドレスはログインIDとしてのみ機能する
- サインアップは閉鎖し、アカウントは Supabase 管理画面から手動で作成する。確認メールは無効化する
- パスワードは設定画面から本人が変更できる。現在のパスワードでログインし直してから更新する。
  Supabase は更新時に本人確認をしないので、端末を離れた隙に変えられないよう自前で確かめる。
  新しいパスワードは8文字以上とする（Supabase 側の下限より厳しくし、送る前に弾く）
- 忘れたときの再設定は持たない。メール送信を必要とするため、GitHub Pages 配信の構成では
  SMTP の用意が要る。管理者が Supabase 管理画面から再設定する
- 全テーブルで RLS を有効化する。公開されるのは JS と Supabase の URL / anon key のみで、
  実際の権限は RLS が決める

### 2.4 共有範囲

**共有範囲は取引が持つ。** 取引・予算・定期登録ルールがそれぞれ `share_group_id` /
`owner_id` を持ち、どちらか一方だけが入る。

**カテゴリは全ユーザー共通のマスタで、共有範囲を持たない。** 「何に使ったか」だけを表す
名前であり、「誰と共有するか」は記録の側が決める。同じ「食費」に夫婦の支出と個人の支出が
並ぶ。カテゴリ名は収支区分ごとに全体で一意になる。

- 共有の単位は共有グループ。「夫婦」「家族全員」のような集合をあらかじめ作っておく
- 取引の `share_group_id` が null なら個人の取引で、`owner_id` の本人だけが見られる
- カテゴリは誰にでも見え、誰でも作れて、誰でも直せる。縛るのは削除だけ（§3.4）
- グループのメンバーは、そのグループの取引を参照・更新・削除できる。
  自分が属さないグループの取引は、存在ごと見えない
- 取引の入力では共有範囲をカテゴリと別に選ぶ。**既定は「個人」**（選択肢の先頭）

カテゴリを共通にする代償は、他人が自分の家計簿の見出しを書き換えられることにある。
改名は禁じない（誤字直しと意味の付け替えを機械では見分けられない）。代わりに、他の人が
使っているカテゴリの改名は影響の件数を見せて確かめる（§3.4）。

### 2.5 SECURITY DEFINER 関数

判定関数は `private` スキーマに置く。ポリシーとトリガの中から呼ぶので `authenticated` に
`execute` を与えざるを得ないが、公開スキーマに置くと PostgREST が
`/rest/v1/rpc/<名前>` としてそのまま外へ出す。`private` は公開スキーマではないので、
ポリシーからは呼べて REST の入口からは消える。`is_group_member_of(gid, uid)` は他人の
uuid を引数に取るため、公開したままだと「利用者 X はグループ Y のメンバーか」を誰でも
問い合わせられる。

| 関数 | 役割 | 本体の条件 |
| --- | --- | --- |
| `private.is_group_member(gid)` | 自分が `gid` のメンバーか | `exists (select 1 from public.share_group_members m where m.share_group_id = gid and m.user_id = auth.uid())` |
| `private.is_group_member_of(gid, uid)` | `uid` が `gid` のメンバーか | 同上の `user_id = uid` |
| `private.accessible_group_ids()` | 自分が属するグループ id（`setof uuid`） | `select share_group_id from public.share_group_members where user_id = auth.uid()` |
| `private.can_access_scope(gid, uid)` | その共有範囲を自分が使えるか | `gid` が null なら `uid = auth.uid()`、そうでなければ `private.is_group_member(gid)` |

DEFINER にする理由は、判定関数では `share_group_members` のポリシーが `is_group_member()` を
呼んで無限再帰するため、書き込み用 RPC（§2.7）では対象表の直接権限を `authenticated` から
外しており INVOKER では関数の中からも書けないため。

- 所有者はテーブルの所有者と揃え、対象テーブルに `force row level security` を掛けない
- すべて `set search_path = ''` とし本文はスキーマ修飾する。判定関数は `stable`
- `revoke execute from public, anon` し、`authenticated` にだけ `grant`。
  スキーマ `private` の `usage` は `authenticated` と `service_role` に与える
  （管理接続の書き込みでもトリガは走り、その中から判定関数を呼ぶ）
- 公開スキーマに置いてよい DEFINER 関数は、画面が呼ぶ RPC（§2.7）の12本だけ。
  この範囲は `supabase/tests/05-exposure.test.sql` で固定する
- **RLS が効かないので権限検査を関数の冒頭で自分で行う**（§2.7）
- `accessible_group_ids()` と `can_access_scope()` の本体条件が全テーブルの唯一の防壁。
  ここを緩めると RLS がまとめて無効化される。カテゴリは全員に開けるので、防壁は
  カテゴリではなく共有範囲の側にある

### 2.6 RLS ポリシーとテーブル権限

取引・予算・定期登録ルールは自分の共有範囲の列で絞る。判定関数を行ごとに呼ぶと
行数だけ関数呼び出しが起きるため、`in (select ...)` で1回の評価（InitPlan）に畳む。

```sql
-- 取引・予算・定期登録ルール
using (owner_id = auth.uid() or share_group_id in (select private.accessible_group_ids()))

-- カテゴリ（全ユーザー共通のマスタ）
using (true)
```

同じ条件を `with check` にも書く。書かないと参照できない共有範囲へレコードを押し込める。

**列の制限は GRANT で行う。** テーブルレベルの UPDATE 権限は全列を含み、そこから
`revoke update (col)` で差し引くことはできない（警告が出て何も起きない）。よってテーブル
レベルでは与えず、許可列を列挙して grant する。**INSERT と UPDATE は別々の権限**なので、
許可列も別々に持つ（片方だけ列挙すると、たとえば `share_group_id` を INSERT で指定できず
`check` 違反でカテゴリを1件も作れない）。列を追加したら grant も更新する。

| テーブル | SELECT | INSERT | UPDATE | DELETE |
| --- | --- | --- | --- | --- |
| profiles | 全ユーザー | 不可（トリガが作る） | 本人のみ。`display_name` / `color` / `default_category_id` | 不可 |
| share_groups | メンバーのみ | RPC のみ | メンバーのみ。`name` | RPC のみ |
| share_group_members | メンバーのみ | RPC のみ | メンバーのみ。`default_weight` / `sort_order` | RPC のみ |
| categories | 全ユーザー | 全ユーザー。`kind` / `name` / `color` / `sort_order` / `parent_id` | 全ユーザー。`name` / `color` / `sort_order` / `is_archived` | RPC のみ |
| transactions | 上のポリシー | RPC のみ | 上のポリシー。`occurred_on` / `payer_id` / `memo` | 上のポリシー |
| transaction_splits | 親の取引に従う | 不可 | 不可 | 不可 |
| budgets | 上のポリシー | 上のポリシー。`category_id` / `share_group_id` / `owner_id` / `month` / `amount` | 上のポリシー。`amount` | 上のポリシー |
| recurring_rules | 上のポリシー（`category_id` 経由） | RPC のみ | RPC のみ | 上のポリシー |
| recurring_rule_splits | 親のルールに従う | 不可 | 不可 | 不可 |
| recurring_postings | 親のルールに従う | 不可 | 不可 | 不可 |

この表の根拠と帰結。

- `categories.is_system` は `default false`、`created_by` は `default auth.uid()` とし、
  いずれも grant しない（`created_by` に NOT NULL は置かない。§3 の `set null` のため）
- `kind` / `parent_id` は INSERT でのみ grant する。したがって収支区分と親は
  作成時にしか決められない。
  **親の付け替えは経路を持たない**（大分類 ⇄ 小分類の入れ替えは、過去の集計の内訳が
  黙って組み変わる。作り直して §5.2 の `move_transactions()` で取引を付け替える）
- `transaction_splits` は SELECT だけ。**DELETE も与えない**（1行だけ消して「合計 ≠ 金額」を
  作れるため）。親の取引を消したときの子行削除は FK のカスケードで行われ、
  子テーブルの DELETE 権限を必要としない
- 取引の INSERT と `amount` / `category_id` / `share_group_id` / `owner_id` の UPDATE を
  直接許すと、負担行の無い取引や合計の合わない取引を作れる（§3.6）。共有範囲を直接
  書き換えられると §5.2 の負担の作り直しも飛ばせる。作成と金額・カテゴリ・共有範囲の
  変更は `upsert_transaction()` と §2.8 の RPC に一本化
- カテゴリの削除は配下の取引を未分類へ移す処理と「自分以外が使っていないこと」の検査を
  伴うため RPC のみ。未分類自体は DELETE を grant しないことで守り、拒否トリガは置かない。
  グループの削除も、配下が空であることの検査を伴うため RPC のみ
- **カテゴリの改名・色・表示順・アーカイブは全ユーザーに開ける。** 共通のマスタであり、
  誤字直しと意味の付け替えを機械で見分ける方法がないため、禁止ではなく確認で守る（§3.4）
- グループ作成直後は自分がまだメンバーではなく、`is_group_member()` を要求するポリシーだけでは
  最初のメンバーを登録できない。作成と初期メンバー登録は `create_share_group()` に閉じる
- メンバーが0人のグループは誰からも見えず配下ごと復旧できない。削除は
  `remove_group_member()` に閉じ、最後の1人は削除できない
- 定期登録ルールも「負担の雛形の合計 = 金額」の不変条件を持つため、作成と更新は
  `upsert_recurring_rule()` に一本化する（§3.9）。削除だけはポリシーで許す。配下の雛形と
  生成の記録は FK のカスケードで消え、生成済みの取引は残る
- `recurring_postings` は「その月はもう作った」ことの唯一の記録なので、書き込みも削除も
  grant しない。手で消せると同じ月の取引がもう一度作られる（§3.9）
- `transaction_splits` の参照だけは親をたどる `exists (...)` になり行ごとの評価が残る（逃げ道は §5.7）

### 2.7 書き込み用の RPC

複数行にまたがる不変条件を持つ操作は関数に閉じる。いずれも DEFINER なので冒頭で検査する。

| 関数 | 役割 | 冒頭で検査すること |
| --- | --- | --- |
| `create_share_group(name, members)` | グループ・メンバー・未分類カテゴリを作る | `members` に呼び出し元自身が含まれ、全員が実在すること |
| `add_group_member(gid, uid, weight, sort_order)` | メンバーを追加する | 呼び出し元が `gid` のメンバー。`uid` が実在しまだメンバーでない。`weight >= 0` |
| `remove_group_member(gid, uid)` | メンバーを外す | 呼び出し元が `gid` のメンバーで、削除後に1人以上残ること |
| `upsert_transaction(...)` | 取引と負担をまとめて書く | `category_id` が実在すること。指定した共有範囲を使えること。**更新なら既存行の共有範囲も**。負担の合計 = 金額。負担の相手と支払者が共有範囲のメンバー（個人の共有範囲のメンバーは本人だけ。§3.6） |
| `category_usage(id)` | 改名・削除の前に見せる影響の件数（§3.4） | `id` が実在すること。返すのは件数だけで、他人の取引の中身は返さない |
| `delete_category(id)` | カテゴリを削除し取引を移す（小分類なら親へ、大分類なら未分類へ。§3.4） | `is_system` でないこと。**小分類が1件も残っていないこと**。**自分以外が作った取引・ルールが0件で、自分から見えない共有範囲の予算も0件であること** |
| `delete_share_group(gid)` | グループを消す | 呼び出し元がメンバー。そのグループの取引と定期登録ルールが0件 |
| `move_transactions(...)` / `move_transactions_scope(...)` | カテゴリ／共有範囲の付け替え | §5.2 の手順（§2.8 の経路ごとに異なる） |
| `import_transactions(rows)` | CSV の一括取り込み（§4.4） | 各行について `upsert_transaction()` と同じ検査 |
| `upsert_recurring_rule(...)` | 定期登録ルールと負担の雛形をまとめて書く | `category_id` が実在し、指定した共有範囲を使えること（**更新なら既存行も**）。雛形の合計 = 金額。負担の相手と支払者が共有範囲のメンバー。`day_of_month` が 1〜31 |
| `run_recurring_rules(today)` | 期日の来た定期登録を取引にする（§5.8） | 参照できる共有範囲のルールだけを対象にすること。1件ごとに `upsert_transaction()` と同じ検査 |

- `created_by` は引数で受け取らず関数の中で `auth.uid()` を入れる。**例外は
  `run_recurring_rules()` が作る取引**で、ここにはルールの `created_by` を引き継ぐ。
  `auth.uid()` にすると、同じ家賃がその月に最初にアプリを開いた人の入力として記録される
- `splits_are_manual` も引数にしない。**負担を引数で受け取ったら true、省略して関数側で
  按分したら false**。フロントが決められると §5.2 の確認が意味を失う

### 2.8 共有範囲の変更

カテゴリは共有範囲を持たなくなったので、**カテゴリの共有範囲を変える**という操作は無い。
経路は2つで、どちらも §2.6 で列を grant していないため RPC を通さずには実行できない。

| 経路 | 担当 | 動くもの | 検査 |
| --- | --- | --- | --- |
| 複数の取引の共有範囲をまとめて変える | `move_transactions_scope()` | 共有範囲だけ（カテゴリは動かない） | §5.2 の手順0・1・3・4 |
| 複数の取引を別のカテゴリへ付け替える | `move_transactions()` | カテゴリだけ（共有範囲は動かない） | 移動先カテゴリの実在と、対象の取引が参照できること |
| 1件の取引を編集する | `upsert_transaction()` | 両方 | 新旧の共有範囲の権限、支払者と負担のメンバー検査（§2.7） |

**負担を作り直すのは、移動元と移動先の共有範囲が異なる場合だけ。** よって
`move_transactions()`（カテゴリの付け替え）では**負担も `splits_are_manual` も常に保たれる**。
未分類 → 食費 のような付け替えで手入力の負担が黙って戻ることはない。
作り直しは §5.1 の既定按分規則に従い、`splits_are_manual` を false に戻す。

## 3. データモデル

金額はすべて円単位の整数（`int`）で持つ。小数は扱わない。

取引入力画面の金額欄だけは四則演算の式（`+ - * /`・括弧・全角記号）を受け取る。式の途中では
小数を許し（`1000*1.08` のような税込計算のため）、結果を四捨五入して整数にしてから保存する。
式が読めない・結果が0以下になる場合は保存できない。CSV の取り込みは式を受け取らない（§4.2）。

`auth.users` を参照する FK の削除規則。**記録に現れる利用者は削除できない。**

| FK | `on delete` | 理由 |
| --- | --- | --- |
| `transactions.payer_id` / `transactions.created_by` / `transactions.owner_id` / `transaction_splits.user_id` / `share_group_members.user_id` / `recurring_rules.owner_id` | `restrict` | 表示名を引けない利用者が集計に現れるのを防ぐ |
| `profiles.id` / `budgets.owner_id` | `cascade` | 記録の無い誤作成アカウントを消せるようにする。予算しか持たない利用者は消せてよい |
| `categories.created_by` / `share_groups.created_by` | `set null` | 作成者が消えても、そのカテゴリ・グループは他の人が使い続ける |

- カテゴリは共有範囲を持たないので、利用者の削除がカテゴリに波及することはない。
  記録がある利用者は `transactions.owner_id` / `created_by` の `restrict` が止める
- `set null` にする2つの `created_by` は **NOT NULL にしない**。NOT NULL のまま `set null` を
  張ると、親を消した瞬間に必ず失敗する。`transactions.created_by` は `restrict` なので NOT NULL でよい
- 家計から抜けるときは `remove_group_member()` で外す（過去の取引は残る。§3.3）

### 3.1 profiles（利用者）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | uuid | PK, FK → auth.users |
| display_name | text | 画面に出す表示名 |
| color | text | 一覧やグラフで本人を識別する色 |
| default_category_id | uuid / null | FK → categories（`on delete set null`）。取引入力の初期値 |
| created_at / updated_at | timestamptz | |

制約：`unique (display_name)` と
`check (display_name = btrim(display_name) and display_name <> '' and display_name not in ('共用','個人') and display_name !~ '[:;[:cntrl:]]')`。
CSV が表示名で人を指すため（§4.2）、`共用` / `個人` を名乗られると支払者が化け、
`:` `;` を含むと負担列を一意に読めない。

`default_category_id` はカテゴリが実在し `is_archived = false` であることをトリガで検査する。
カテゴリは全ユーザー共通になったので、参照権限の検査は要らなくなった。

RLS：`authenticated` なら全員が参照でき、更新は本人のみ（表示名の解決に使うため参照は絞らない）。

行は `auth.users` への INSERT トリガ（DEFINER）で作る。**未分類カテゴリは利用者ごとには
作らない**（未分類は収支区分ごとに全体で1件。§3.4）。表示名の初期値はメールアドレスの
ローカル部とし、**既存と重なるときや予約語に当たるときは `-2`、`-3` と連番を付けて必ず成功させる**。

### 3.2 share_groups（共有グループ）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | uuid | PK |
| name | text | グループ名 |
| created_by | uuid / null | FK → auth.users。作成者が削除されると null |
| created_at / updated_at | timestamptz | |

制約：`unique (name)`、`check (name = btrim(name) and name <> '' and name <> '個人')`。
CSV がグループ名で共有範囲を指すため（§4.2）、`個人` を名乗られるとグループか個人かを
読めなくなる。メンバーが直接 UPDATE できる列なので、約束ではなく制約で縛る。

### 3.3 share_group_members（メンバーと既定割合）

| 列 | 型 | 説明 |
| --- | --- | --- |
| share_group_id | uuid | PK, FK → share_groups |
| user_id | uuid | PK, FK → auth.users |
| default_weight | int | 既定の負担割合の重み。0 以上 |
| sort_order | int | 表示順 |

- 折半なら全員 `1`、7:3 なら `7` と `3`。重みの合計に決まった値はない
- `default_weight = 0` のメンバーは既定では負担しないが取引は見られる
- 削除は `remove_group_member()` 経由に限り、最後の1人は削除できない（§2.6）
- メンバーの追加・削除は既存の取引の負担を変えない。メンバー検査は書き込み時にしか
  行わない（§3.5）ため、脱退した人が支払者・負担者として残る取引が存在しうる
- 集計で人ごとに並べる対象は、現メンバーと、その共有範囲のデータに現れる利用者
  （支払者・負担者）の和集合

### 3.4 categories（カテゴリ）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | uuid | PK |
| created_by | uuid / null | FK → auth.users。作成者が削除されると null |
| parent_id | uuid / null | FK → categories（`on delete restrict`）。null なら大分類、非 null なら小分類 |
| kind | text | `income` / `expense`。小分類は親と同じ値 |
| name | text | カテゴリ名 |
| color | text | グラフの色。小分類の色は内訳を展開したときだけ使う（§5.5） |
| sort_order | int | 同じ親の中での表示順。昇順、同値なら名前順で並べる |
| is_system | bool | 「未分類」。作成後は変更できない（§2.6） |
| is_archived | bool | 使用停止。既存の取引は残したまま新規選択から外す |
| created_at / updated_at | timestamptz | |

制約：`check (name = btrim(name) and name <> '')`、
`check (not (is_system and parent_id is not null))`（未分類は小分類になれない）、
および部分一意インデックス。

```sql
-- 大分類は収支区分の中で一意（全ユーザー共通のマスタなので、範囲ごとの重複が無くなった）
create unique index categories_root_uq on public.categories (kind, name)
  where parent_id is null;
-- 小分類は同じ親の中で一意。収支区分は親と一致するため親だけで足りる
create unique index categories_child_uq on public.categories (parent_id, name)
  where parent_id is not null;
-- 未分類は収支区分ごとに1つ
create unique index categories_sys_uq on public.categories (kind) where is_system;
```

大分類の一意インデックスに `where parent_id is null` を付けないと、`食費 / 外食` と
`日用品 / 外食` を並べられない。

`name` の trim は制約にする（アプリ側だけだと `"食費 "` と `"食費"` が共存し、
一意インデックスが発火せず §4.4 のカテゴリ解決が2件にマッチする）。

- アーカイブ済みも一意性の判定に含める（同名を作り直すにはアーカイブを解除する）
- 表示順はカテゴリ画面で入れ替える。入れ替えると**同じ親の中**（大分類なら同じ収支区分の
  大分類どうし、小分類なら同じ親の小分類どうし）で 10 刻みに振り直す。
  追加したカテゴリは末尾に付く。未分類は `sort_order = 9999` に固定し、並べ替えの
  対象にしない（常に末尾）
- `kind` は変更できない（過去の集計の符号が全部ひっくり返り、収支をまたぐ付け替えは
  取引ごとに意味が違う）。間違えたときは別のカテゴリを作って取引を付け替える
- **未分類は収支区分ごとに全体で1つ**（`is_system = true`）。移行時に共有範囲ごとの未分類を
  1件へ寄せ、以後は誰かを追加してもグループを作っても増えない。アーカイブ・改名は
  `is_system` 行に対してトリガで拒否する。削除は DELETE を grant しないことで守る

#### 改名と削除（列22・列23・列25・列26）

カテゴリは全員のものなので、**改名・色・表示順・アーカイブは誰でもできる**。作成者かどうかも
問わない。禁じるのは削除だけで、条件は次のとおり。

- **自分以外が作った取引・定期登録ルールが0件**であること
- **自分から見えない共有範囲の予算が0件**であること

削除すると他人の取引が黙って未分類へ移り、他人の予算が消える。取り返しがつかないのはここ
なので、ここだけを止めてアーカイブへ誘導する。アーカイブは無損失で可逆な代替になる。

**改名は止めない。** 誤字直し（食費 → 食料費）と意味の付け替え（食費 → 交際費）を機械で
見分ける方法はなく、止めると前者まで永久にできなくなる。代わりに `category_usage(id)` が
影響の件数を返し、他の人が使っているカテゴリを改名するときは画面が保存前に見せて確かめる。

```
{ transactions, others_transactions, rules, others_rules, budgets, others_budgets, others }
```

自分に見えない共有範囲の分も数えるため DEFINER で数える。**返すのは件数だけ**で、他人の
取引の中身は返さない。

#### 3.4.1 小分類

**階層は2段まで。** 大分類（`parent_id is null`）とその小分類だけを持ち、孫は作れない。

- **小分類の `kind` は親からコピーする。** BEFORE INSERT トリガが親の行を読んで上書きし、
  送られてきた値は捨てる。共有範囲は親からも引き継がない（カテゴリは持たない）
- 親として指定できるのは、`parent_id is null` かつ `is_system = false` の行だけ。
  どちらもトリガで拒否する。深さ2の固定はこの検査だけで保たれる（親になれるのは
  大分類だけなので、小分類の下には何も付かない）
- **取引は大分類にも小分類にも付けられる。** 小分類は任意で、`食費` のまま記録してよい。
  既存の取引・`profiles.default_category_id`・未分類はすべて大分類のままで動く
- アーカイブは行ごとに持つが、**親がアーカイブ済みなら配下の小分類も新規選択から外す**
  （子の `is_archived` は書き換えない。親のアーカイブを解除したら子も元の状態で戻る）
- 削除（`delete_category()`）の移動先は、小分類なら**親**、大分類なら未分類とする。
  取引は自分の共有範囲を持ったまま動くので、**負担は作り直さない**（§2.8）。
  **小分類が残っている大分類は削除できない**（先に小分類を消す。取引が親へ集まる）。
  `parent_id` の FK が `restrict` なのはこの検査を DB でも二重に持つため

### 3.5 transactions（取引）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | uuid | PK |
| category_id | uuid | FK → categories。必須。収支区分はここから決まる |
| share_group_id | uuid / null | FK → share_groups。共有範囲。null なら個人 |
| owner_id | uuid / null | FK → auth.users。個人の取引のときだけ入る |
| payer_id | uuid / null | FK → auth.users。支払った人。null は「共用」 |
| created_by | uuid | FK → auth.users。入力した人 |
| occurred_on | date | 取引日。対象月はこの列から決まる |
| amount | int | 金額。正の整数（収支の向きはカテゴリの `kind` が持つ） |
| splits_are_manual | bool | 負担を手入力で編集したか（§5.2 の確認に使う） |
| memo | text | 備考 |
| created_at / updated_at | timestamptz | |

制約：`check (amount > 0)`、`check (num_nonnulls(share_group_id, owner_id) = 1)`。
支払者はトリガで検査する。

- 個人の取引（`share_group_id is null`）なら `payer_id = owner_id`。**null は許さない**
- 共有の取引なら `payer_id is null`（共用）か、共有範囲のメンバーであること

null を無検査で通すと `update({payer_id: null})` だけで個人の取引を「共用」にでき、
§5.4 の集計が崩れる。

トリガは **INSERT 時と、`payer_id` または共有範囲が実際に変わる UPDATE 時にだけ**
発火させる（脱退した人が支払者の過去の取引を、備考の修正だけで保存できなくしないため）。
`update of payer_id, share_group_id, owner_id` は「SET 句に現れたら発火」なので
`when (old.payer_id is distinct from new.payer_id or ...)` を付ける。
`when` の書き分けのため INSERT 用と UPDATE 用の2本に分ける。

インデックス：`(occurred_on)`、`(category_id, occurred_on)`、`(payer_id)`、
`(share_group_id, owner_id, occurred_on)`（RLS が毎回引く）。

収支区分をカテゴリから複製しないため、同期トリガも不一致もない。共有範囲での絞り込みは
自分の列で直接行う。

カテゴリは必須。分類が決まらないときはその収支区分の「未分類」を選ぶ。収入も同じ表で
扱い、共有の収入は「支払者 = 受け取った人」、負担は「誰の取り分として数えるか」を表す。

### 3.6 transaction_splits（負担）

| 列 | 型 | 説明 |
| --- | --- | --- |
| transaction_id | uuid | PK, FK → transactions（`on delete cascade`） |
| user_id | uuid | PK, FK → auth.users |
| amount | int | 負担額。0 以上 |

- すべての取引が負担行を持つ。個人の取引は本人1行（`amount = 取引の金額`）
- 負担額の合計は取引の `amount` に一致する。この不変条件は行トリガでは書けない
  （2行目を書く前に1行目で必ず不一致になり、取引の INSERT 時点では負担行が存在しない）。
  よって**取引と負担は `upsert_transaction()` でまとめて書き、関数の末尾で1回だけ検査する**。
  取引の INSERT と `amount` / `category_id` の UPDATE、負担の直接書き込みは grant しない（§2.6）
- 負担の相手は書き込み時点で**取引の**共有範囲のメンバーであること。
  **個人の共有範囲のメンバーは `owner_id` 1人だけ**なので負担は本人1行に限る。
  `is_group_member(null)` は false になるため、ここを書かないと「個人では検査不要」と
  読まれ、自分の個人取引に他人の負担行を積める（その行は本人からは見えず、集計だけが狂う）
- 参照権限は親の取引に従う

### 3.7 budgets（予算）

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | uuid | PK |
| category_id | uuid | FK → categories。必須 |
| share_group_id | uuid / null | FK → share_groups。共有範囲。null なら個人 |
| owner_id | uuid / null | FK → auth.users。個人の予算のときだけ入る |
| month | date | 対象月。その月の1日を入れる |
| amount | int | 上限額 |
| created_at / updated_at | timestamptz | |

制約：`check (num_nonnulls(share_group_id, owner_id) = 1)`、`check (amount > 0)`、
`check (month = date_trunc('month', month)::date)`。`month` は INSERT で grant しているため、
月初でない日付を直接入れると一意制約をすり抜けて同じ対象月の予算行が複数でき、§5.6 の
消化率がどれを使うか決まらなくなる。約束ではなく制約で縛る。

- **予算は大分類にのみ置く**（`parent_id is null`。トリガで検査する）。「食費に月5万」は
  外食も含んだ枠であり、親と小分類の両方に置けると同じ支出が2つの枠に数えられて
  §5.6 の消化率がどちらを指すか決まらなくなる。小分類ごとの消化は集計画面の内訳で見る
- 予算はカテゴリごとにのみ置く。共有範囲全体の枠は持たず、必要なら合計を画面で出す
- **一意性は（カテゴリ, 共有範囲, 対象月）**。カテゴリが全ユーザー共通になったため、
  同じ「食費」に夫婦の枠と個人の枠が並ぶ。単一の unique は NULL 同士が衝突せず一度も
  発火しないので、部分一意インデックスに分ける（§3.4 と同じ理由）
- 予算画面は共有範囲を1つ選んで表を作る。行は（カテゴリ × その範囲）になる
- 支出のみを対象とし、収入カテゴリには置けない（トリガで検査）
- 予算なしは「行が無い」ことで表す。0 円の行は作れない

### 3.8 recurring_rules（定期登録ルール）

家賃のように毎月同じ日に同じ額で出ていく支出の雛形。取引そのものではなく、取引を作るための
設定を持つ。

| 列 | 型 | 説明 |
| --- | --- | --- |
| id | uuid | PK |
| category_id | uuid | FK → categories。必須。収支区分はここから決まる |
| share_group_id | uuid / null | FK → share_groups。共有範囲。null なら個人 |
| owner_id | uuid / null | FK → auth.users。個人のルールのときだけ入る |
| payer_id | uuid / null | FK → auth.users。支払う人。null は「共用」 |
| amount | int | 毎月の金額。正の整数 |
| day_of_month | int | 支払日。1〜31。その月に無い日は月末日に丸める（§5.8） |
| memo | text | 作る取引の備考 |
| start_month | date | 生成を始める対象月。その月の1日を入れる |
| end_month | date / null | 生成を終える対象月。null は無期限 |
| is_paused | bool | 一時停止しているか |
| splits_are_manual | bool | 負担の雛形を手で決めたか |
| created_by | uuid | FK → auth.users。作った人 |
| created_at / updated_at | timestamptz | |

制約：`check (amount > 0)`、`check (day_of_month between 1 and 31)`、
`check (start_month = date_trunc('month', start_month)::date)`（`end_month` も同じ）、
`check (end_month is null or start_month <= end_month)`。支払者は取引と同じ規則をトリガで
検査する（個人なら `payer_id = owner_id`、共有なら null かメンバー。§3.5）。

- **周期は毎月のみ、金額は固定**。隔月・毎年や変動額は扱わない。光熱費のように毎月変わるものは
  手で入力する。金額が変わった月は、生成された取引をその月だけ編集する
- 金額は必須。取引の `amount` は正の整数（§3.5）なので、金額を持たない「予定」は取引として
  保存できず、別の持ち方が要る。初版では持たない
- `created_by` は `restrict`。生成する取引の `created_by` に引き継ぐため、消せては困る（§2.7）
- 消すのではなく `end_month` を置くことを勧める。消して作り直すと生成の記録も消えるため、
  同じ対象月にもう一度取引が作られる

### 3.9 recurring_rule_splits / recurring_postings

**recurring_rule_splits（負担の雛形）**

| 列 | 型 | 説明 |
| --- | --- | --- |
| rule_id | uuid | PK, FK → recurring_rules（`on delete cascade`） |
| user_id | uuid | PK, FK → auth.users |
| amount | int | 負担額。0 以上 |

`splits_are_manual` が true のルールだけが行を持ち、合計はルールの `amount` に一致する。
false のルールは行を持たず、生成のたびに §5.1 で按分する。取引の負担と同じく、この不変条件は
行トリガでは書けないため `upsert_recurring_rule()` の末尾で1回だけ検査する（§3.6）。

**recurring_postings（生成の記録）**

| 列 | 型 | 説明 |
| --- | --- | --- |
| rule_id | uuid | PK, FK → recurring_rules（`on delete cascade`） |
| month | date | PK。生成した対象月。その月の1日 |
| transaction_id | uuid / null | FK → transactions（`on delete set null`）。生成した取引 |
| created_at | timestamptz | |

- `(rule_id, month)` の主キーが**同じ対象月に2度作らないこと**を保証する。複数人が同時に
  アプリを開いても、2件目の挿入が競合して何もしないだけで済む（§5.8）
- `transaction_id` は `set null`。生成した取引を消しても記録は残り、次に開いても復活しない。
  代わりに取引側へ「どのルールから来たか」の列を持たせて一意にすると、**意図して消した取引が
  黙って戻ってくる**。生成済みかどうかは取引の有無ではなくこの表で判断する
- `month` は `check (month = date_trunc('month', month)::date)`

### 3.10 リレーション

```text
auth.users
  ├─ profiles (1:1)
  ├─ share_groups ─┬─ share_group_members
  │                └─ categories（共有）
  └─ categories（個人）

categories ─┬─ transactions ── transaction_splits
            ├─ budgets
            └─ recurring_rules ─┬─ recurring_rule_splits
                                └─ recurring_postings ── transactions
```

| FK | `on delete` | 理由 |
| --- | --- | --- |
| `share_group_members.share_group_id` | `cascade` | グループを消したらメンバーも消える |
| `categories.share_group_id` | `cascade` | 同上。残るのは未分類だけなので支障がない |
| `budgets.category_id` | `cascade` | 未分類にも予算を置けるため、`no action` だとグループ削除が必ず失敗する |
| `categories.parent_id` | `restrict` | 小分類の取引を親へ移すのは `delete_category()` の仕事。黙って消させない |
| `transactions.category_id` | `restrict` | 取引を未分類へ移すのは `delete_category()` の仕事。黙って消させない |
| `transaction_splits.transaction_id` | `cascade` | 取引を消したら負担も消える |
| `recurring_rules.category_id` | `restrict` | カテゴリ削除時にルールを付け替えるのは `delete_category()` の仕事。黙って消させない |
| `recurring_rule_splits.rule_id` / `recurring_postings.rule_id` | `cascade` | ルールを消したら雛形も生成の記録も消える（作った取引は残る） |
| `recurring_postings.transaction_id` | `set null` | 生成した取引を消しても「その月は作った」記録を残す（§3.9） |

- カテゴリの削除は `delete_category()` に閉じ、配下の取引と定期登録ルールを移動先（小分類なら親、
  大分類なら同じ収支区分の「未分類」）へ移し、そのカテゴリの予算を消してから削除する。
  取引の `category_id` は grant していないため、この付け替えは DEFINER 関数の中でしか
  行えない。**自分以外が使っているカテゴリは削除できず**、アーカイブを促す（§3.4）
- カテゴリはグループに属さないため、グループの削除がカテゴリに波及することはない
- グループは、そのグループの取引・定期登録ルールがひとつでも残っている限り削除できない。
  削除するとメンバーと、そのグループの予算が消える

## 4. データ形式

### 4.1 CSV の共通仕様

- UTF-8（BOM 付き。Excel でそのまま開けるようにする）、改行は CRLF、区切りは `,`
- 値に `,` `"` 改行のいずれかを含む場合のみ `"` で囲み、内側の `"` は `""` にする
- 1行目はヘッダ行。列はヘッダ名で解決するため並び順は問わない

### 4.2 取引 CSV

エクスポートとインポートで同じ列を使う。

```text
日付,収支,共有範囲,カテゴリ,小分類,金額,支払者,負担,備考
2026-08-31,支出,夫婦,家賃,,120000,共用,たかし:60000;はなこ:60000,8月分
2026-08-31,支出,夫婦,食費,,4200,はなこ,たかし:2100;はなこ:2100,まとめ買い
2026-08-31,支出,個人,食費,外食,780,たかし,たかし:780,昼食
```

| 列 | 値 |
| --- | --- |
| 日付 | `YYYY-MM-DD` |
| 収支 | `収入` / `支出` |
| 共有範囲 | 共有グループ名。`個人` なら自分の個人の共有範囲。**取引の共有範囲**を指す |
| カテゴリ | 大分類の名前。収支区分と併せて大分類を一意に決める（カテゴリは全ユーザー共通） |
| 小分類 | 小分類の名前。空欄なら大分類そのものに付ける。取り込みでは列ごと無くてもよい |
| 金額 | 正の整数。桁区切りと通貨記号は取り込み時のみ許容し、書き出しでは付けない |
| 支払者 | 表示名。`共用` なら支払者なし（表示名には使えない予約語） |
| 負担 | `表示名:金額` を `;` で連結。合計は金額に一致すること。取り込み時は空欄可（既定割合で按分）、書き出しでは常に明示する |
| 備考 | 任意 |

`小分類` 列は取り込みでのみ省略できる（列をヘッダ名で解決するため、無ければ全行が空欄と
同じ扱いになり、下位分類を入れる前に書き出したファイルもそのまま取り込める）。書き出しでは
常に出力し、小分類の無い取引は空欄にする。

取引 ID の列は持たない。CSV は**新規の取り込みと控えの書き出しのための形式**であり、
書き出して直して戻すための更新手段ではない。既存の取引はアプリ上で編集する。

### 4.3 その他の CSV

いずれも書き出し専用。共有範囲の指し方は取引 CSV に揃える（グループ名、または `個人`）。
**カテゴリ CSV は共有範囲の列を持たない**（カテゴリは全ユーザー共通。§2.4）。予算は
共有範囲を持つので列が残る。

```text
# カテゴリ（小分類も1行として書き出す。共有範囲の列は無い）
収支,カテゴリ,小分類,色,表示順,未分類,アーカイブ済み
支出,家賃,,#e11d48,10,いいえ,いいえ
支出,食費,外食,#f59e0b,10,いいえ,いいえ

# 予算（大分類のみ。§3.7）
共有範囲,収支,カテゴリ,対象月,予算額
夫婦,支出,家賃,2026-08,120000

# 共有グループ（メンバー1人を1行として書き出す）
グループ,メンバー,負担割合,表示順
夫婦,たかし,1,10
夫婦,はなこ,1,20
```

対象月は `YYYY-MM`（日付ではないため）。未分類・アーカイブ済みは `はい` / `いいえ`。
カテゴリ CSV では小分類も1行として書き出し、`表示順` はその行の `sort_order`
（小分類なら同じ親の中での順）をそのまま入れる。親の行を先に、続けてその小分類を並べる。

### 4.4 CSV インポート

インポートできるのは取引 CSV だけ。

1. ヘッダ名から列位置を決める
2. **全行を先に検証する。** 次に当たる行はエラーとして印を付け、投入しない
   - 日付・収支の書式が不正、金額が1以上の整数でない
   - 共有範囲のグループが存在しない、または自分がそのメンバーでない
   - 収支 + カテゴリ名（+ 小分類名）でカテゴリを解決できない
     （手順3の選択後にも解決しない）。**共有範囲では絞らない**（カテゴリは全ユーザー共通）
   - 支払者・負担者が存在しない、または共有範囲のメンバーでない
   - 支払者が `共用` なのに共有範囲が `個人` である
   - 共有範囲が `個人` なのに、支払者が自分でない、または自分以外の負担がある
   - 負担列の書式が不正、負担の合計が金額と一致しない、同じ人が2回現れる
     （`transaction_splits` の PK に当たる）、0未満の負担額がある（合計が一致していても通さない）
3. カテゴリが見つからない場合は、新規作成するか「未分類」にするかを選ぶ。作成の単位は
   「大分類」または「大分類 + その下の小分類」で、`小分類` 列だけが未知なら**既存の大分類の
   下に小分類を作る**（大分類ごと作り直さない）。「未分類」を選んだ行は小分類を捨て、
   その収支区分の未分類（大分類）に付ける
4. 「負担」列が空欄の行は、共有の取引なら既定割合で按分し（§5.1）、個人なら本人が全額
5. 既存取引との重複（日付・収支・共有範囲・カテゴリ・小分類・金額・支払者・負担・備考が
   すべて一致。解決後のカテゴリ id が一致すること、と言い換えてよい）は
   候補として提示し、取り込む / 飛ばすを選ぶ。**負担は手順4の按分後の値で比較する**
   （生値で比べると空欄の行は決して一致せず、同じファイルを2回取り込むと二重登録される）
6. 検証を通った行だけを `import_transactions()` に渡し、1トランザクションで投入する
7. 結果を「成功 / 飛ばした / エラー」の件数と行番号つきで表示する

エラー行があっても、検証を通った行の取り込みは行う。検証を全行ぶん先に済ませるため、
投入そのものは途中で失敗しない。

### 4.5 エクスポート

- 取引・カテゴリ・予算・共有グループの CSV を選んで出力できる
- 期間を指定できるのは取引と予算だけ。「全期間」または対象月の範囲を選ぶ
- 参照できるレコードだけを出力する
- 定期登録ルールは入出力の対象に含めない。CSV の取引はすでに確定した記録であり、
  雛形を取り込むと取引と区別できないため

## 5. 算出ルール

### 5.1 負担の按分

共有範囲がグループの取引で負担を自動計算するとき、次の手順で整数円に割り付ける。

1. 対象は `default_weight > 0` のメンバー。重みの合計を `W`、取引の金額を `A` とする
2. 各メンバーの仮の負担額を `floor(A * weight / W)` とする
3. 残った差額（`A` − 仮の負担額の合計）を、重みの大きい順に1円ずつ配る。
   重みが同じなら `sort_order` の昇順、それも同じなら `user_id` の昇順
4. 結果の合計は必ず `A` に一致する（例：`A = 1001` の折半は 501 円と 500 円）

- `W = 0`（重み > 0 のメンバーが1人もいない）ときは支払者が全額を負担する。
  支払者が「共用」ならメンバー全員を重み1として按分する
- 個人の共有範囲の取引は本人が全額を負担する1行になる
- **収入は既定では受け取った本人の 100%。** 支出用の重みを取り分に流用しない。
  ただし支払者が「共用」の収入は受け取った本人がいないため、`default_weight > 0` の
  メンバーで按分する（`W = 0` なら全員を重み1）
- 手入力で編集する場合も、合計が金額に一致しない限り保存できない。1人だけ金額を入れて
  残りを自動で埋める操作を用意する。手入力した取引は `splits_are_manual = true` とする

### 5.2 共有範囲の変更

取引の共有範囲の変更と、カテゴリの付け替えは、1つの RPC の中で原子的に行う。
行ごとに更新すると権限のない行が黙って残り部分適用になるため、この手順に集約する
（§2.6 で列を grant していない）。経路ごとにどの手順を課すかは §2.8。

カテゴリは共有範囲を持たないので、**動かすのは取引の側だけ**。統合も、移動先の同名カテゴリの
検査も、移動元カテゴリの削除も無くなった。

0. **呼び出し元の権限を検査する。** 対象の取引がすべて自分の参照できる共有範囲にあり、
   移動先の共有範囲にも呼び出し元が属すること（グループなら `is_group_member(移動先)`、
   個人なら移動先の `owner_id = auth.uid()`）。DEFINER は RLS が効かないため、これを書かないと
   id を知っているだけで他人のグループへ押し込める。支払者の検査（手順3・4）は「共用」だけの
   取引を素通りさせるので代わりにならない
1. 移動対象の取引を数える
2. 移動先が個人のとき、支払者が自分でない取引（「共用」を含む）、または自分以外の負担がある
   取引が1件でもあれば、該当件数を示して中止する
3. 移動先がグループのとき、支払者が移動先グループのメンバーでない取引が1件でもあれば、
   該当件数を示して中止する。支払者が「共用」の取引は共有から共有への移動では許す
   （共有から個人への移動は手順2で弾く）
4. 対象の取引の `share_group_id` / `owner_id` を移動先に変える
5. 共有範囲が実際に変わった取引にかぎり、負担を **§5.1 の既定按分規則**で作り直し、
   `splits_are_manual` を false に戻す（§2.8）。収入は受け取った本人 100%（共用なら按分）であり、
   支出用の `default_weight` をそのまま当てはめない

**カテゴリの付け替え（`move_transactions()`）は共有範囲を動かさない。** よって手順2〜5は
課さず、負担も `splits_are_manual` もそのまま保たれる。未分類 → 食費 のような付け替えで
手入力の負担が黙って戻ることはない。

予算は取引とは別に共有範囲を持つため、取引を移しても付いて動かない。移した先の枠に
入れ直したいときは予算画面で置き直す。

実行前の確認では、移動する取引の件数と金額を示す。共有範囲が変わる場合は
`splits_are_manual` の件数を添える。

### 5.3 対象月

- 取引の対象月は `occurred_on` の年月とする。締め日の概念は持たない
- 月の境界はローカルタイムゾーン（`Asia/Tokyo`）で判定する

### 5.4 集計の軸

集計画面は2つの軸を持つ。予算の実績は §5.6 で固定であり、この軸には従わない。

| 軸 | 選べる値 |
| --- | --- |
| 対象範囲 | 自分に関わるすべて / 共有グループごと / 個人のみ |
| 集計基準 | 負担額（既定） / 支払額 |

**対象の利用者**は、対象範囲が「共有グループごと」ならそのグループの集計対象の利用者すべて
（§3.3 の和集合）、「自分に関わるすべて」「個人のみ」なら自分自身を指す。
**集計対象額**は、負担額基準では対象の利用者の `transaction_splits.amount`、支払額基準では
`payer_id` が対象の利用者である取引の `amount`。負担額基準では取引ではなく負担の行が単位になる。

- 対象範囲は取引の共有範囲で絞る
- 支払額基準では `payer_id = null`（共用）の取引を「共用」の枠にまとめ、人と並べて表示する
- グループ単位で見るときは、どちらの基準でも合計はグループの支出総額に一致する
  （支払額基準では「共用」の枠を含めて一致）
- 「自分に関わるすべて」は、個人の取引と、自分が属するグループでの自分の負担
  （または支払）の合計。支払額基準では共用の取引が誰にも属さないため、この値を人数ぶん
  足してもグループの支出総額にはならない
- カテゴリ別の内訳は**カテゴリ × 共有範囲**で1行にする。カテゴリが全ユーザー共通に
  なったため、同じ「食費」に夫婦の支出と個人の支出が入る。カテゴリだけで畳むと
  2つの財布の話が1行に混ざり、行に付く共有範囲の印がどちらを指すか決まらなくなる
- **カテゴリ別の内訳は大分類で集約する。** 大分類の額は、その大分類そのものに付いた取引と
  配下の小分類の取引の合計。行を開くと小分類の内訳が出る（大分類に直接付いた分は
  「（小分類なし）」の行として並べる）。円グラフ・月次推移・前月比は大分類の単位で描く

### 5.5 月次集計

対象月・対象範囲・集計基準を決めたうえで次を求める。

| 値 | 定義 |
| --- | --- |
| 収入合計 | 収入カテゴリの取引の集計対象額の合計 |
| 支出合計 | 支出カテゴリの取引の集計対象額の合計 |
| 収支 | 収入合計 − 支出合計 |
| カテゴリ別支出 | 大分類ごとの合計（配下の小分類を含む）。降順に並べる。行を開くと小分類の内訳が出る |
| 人別支出 | グループを見ているときの利用者ごとの合計（対象は §3.3。支払額基準では「共用」の枠を含む） |
| 前月比 | 当月の支出合計 − 前月の支出合計 |

### 5.6 予算の消化

予算の実績は、集計基準によらず**そのカテゴリの対象月の支出総額（配下の小分類を含む）**とする。
予算は大分類にしか置けない（§3.7）ため、実績も大分類そのものに付いた取引と配下の小分類の
取引の合計になる。予算画面では消化率とあわせて小分類ごとの実績を内訳として出す。共有の予算は
「夫婦で家賃に月12万」という共同の枠であり、負担額基準にすると枠が人数分に割れて意味を失うため。

- 自分の負担は参考値として併記する（消化率の計算には使わない）
- 消化率 = 実績 ÷ 予算。予算の行が無いカテゴリは「予算なし」として扱う
- 残額 = 予算 − 実績。負の値は超過として表示する
- 予算は月をまたいで繰り越さない。前月の予算を複製する操作を用意する
- 共有範囲ごとの合計欄に、その範囲の予算と実績の合計を出す

### 5.7 集計の実行場所と取得件数の上限

PostgREST は1リクエストの返却行数に上限がある（本番はプロジェクトの API 設定で決まる）。
超えてもエラーにならず黙って打ち切られるため、件数はサーバ側で数え、中身が要るところは
`src/lib/paged.ts` で分割して取り切る。月次集計のような合計値は DB 側で求める。

- ビューには `with (security_invoker = true)` を付ける。付けないと所有者権限で動き、
  RLS を素通りして他グループの合計まで返す
- 集計関数は SECURITY INVOKER を既定とする。やむを得ず DEFINER にする場合は関数の中で
  `is_group_member()` を検査する
- `transaction_splits` の RLS だけは親の取引をたどる行ごとの評価になる（§2.6）。
  負担額基準の集計はこの表を最も多く読むため、実測で遅い場合は `transaction_splits` に
  `category_id` を持たせ（取引からのコピー、変更経路は RPC のみ）、取引と同じ
  `owner_id = auth.uid() or share_group_id in (select accessible_group_ids())` で絞れるようにする

### 5.8 定期登録の生成

`run_recurring_rules(today)` が、期日の来た定期登録ルールを取引にする。アプリの起動時に1回
呼び、設定画面から手で実行することもできる。**サーバーを持たない**ため（§2.2）、生成の起点は
アプリを開いた誰かになる。集計と予算は対象月の単位で見る（§5.3）ので、月の途中で遡って
入っても結果は変わらない。

対象は、次をすべて満たす（ルール, 対象月）の組。対象月の古い順に処理する。

1. ルールの共有範囲が自分の参照できるものであり、カテゴリがアーカイブされていない
2. `is_paused` が false
3. `start_month <= 対象月`。`end_month` があれば `対象月 <= end_month`
4. その対象月の**予定日が `today` 以下**。予定日はルールの `day_of_month`、その月に無ければ月末日
5. `recurring_postings` に `(rule_id, 対象月)` の行が無い

作る取引は `upsert_transaction()` と同じ検査を通す。`occurred_on` は予定日、`amount` /
`payer_id` / `memo` はルールの値、負担は `splits_are_manual` が true ならルールの雛形の複製、
false なら §5.1 の既定按分。書けたら `recurring_postings` に1行残す。

- **未来の予定は作らない。** 先に入れると、まだ払っていない支出が集計と予算の消化に現れる
- 遡りの上限は置かない。数ヶ月開かなくても、条件を満たす月をすべて作る
- 二重登録は `unique (rule_id, month)` が止める。2人が同時に開いても2件目は何もしない（§3.9）
- **失敗はルール単位で捕まえ、そのルールだけ飛ばして残りを続ける**（支払者がグループを
  抜けた場合など）。1件の失敗で他の固定費まで入らなくなる方が困る
- 戻り値は「生成した件数・失敗した件数・失敗したルール」。ホーム画面がこれを知らせる。
  黙って増えると、覚えのない取引が並んだように見える
- 生成された取引は普通の取引で、編集も削除もできる。**削除しても再生成しない**（§3.9）
- ルールのカテゴリが別の共有範囲へ移ったときは、雛形の負担も作り直して
  `splits_are_manual` を false に戻す（§5.2 と同じ理由）

## 7. 仕様の管理方法（決定表）

機能の振る舞いは観点ごとの決定表として `spec/tables/*.jsonl` に持つ。

### 7.1 決定表の構成

1つの決定表は5つのブロックからなる。

| ブロック | 内容 |
| --- | --- |
| 条件 | 前提となる状態・入力 |
| 操作 | ユーザーの操作 |
| 結果 | 期待される結果 |
| ユニットテスト | 対応するユニットテスト |
| E2Eテスト | 対応する E2E テスト |

- 行がブロックの要素、列が1つの条件の組み合わせを表す
- 1列 = 1テストケース（1つの `it` ブロック）とする。1つの列が結果を複数持ってよい
- セルには ○ / × / 空欄 のいずれかが入る
- 行タイトルは2列で表示してよい
- 正常系・境界値・異常系をすべて列として持つ。決定表だけを見て、画面デザインを除く全ての機能を再現できることを目標とする

### 7.2 実体（jsonl）

1列を1行として表す。○×ではなく行タイトルをそのまま持つ。

- ファイルは観点ごとに分け、ファイル名の昇順に表示する。1つのファイルに複数の決定表を書いてよい
- `table` が決定表の名前、`col` が列番号。同じ決定表の中で列番号は重複できない
- ブロックは `conditions` / `actions` / `results` / `unit` / `e2e` の5つ
- 各ブロックは、成立する行タイトルを `true`、明示的に不成立の行タイトルを `false` に置く。どちらにも現れない行タイトルが空欄になる
- ブロックの値を配列で書くと、すべて `true` の意味になる
- 行タイトルが2列になるものは `カテゴリ:共有` のようにコロン区切りの1文字列で持ち、HTML 生成時に最初のコロンで分割して2列にする。コロンを含まない行タイトルは2列ぶんを使って表示する
- 行の並びは、その決定表の列を番号順に走査したときの初出順になる
- 任意で `note` を持てる。列に対する補足で、表の下に列番号つきで並ぶ

```jsonl
{"table":"負担の按分","col":1,"conditions":{"true":["カテゴリ:共有","割合:折半","金額:割り切れない"]},"actions":{"true":["取引を保存する"]},"results":{"true":["負担:重みの大きい順に1円ずつ寄せる","負担:合計が金額に一致する"]},"unit":["splitAmount: 1001円の折半は501と500になる"],"e2e":["transaction.spec: 折半の端数が先頭メンバーに寄る"]}
```

### 7.3 表示用HTML

`spec/build-tables.ts` が `spec/tables/*.jsonl` を読んで `spec/dist/index.html` を生成する。

```text
cd spec && npm run build
```

- 各決定表の上に列番号の数値入力欄があり、入力するとその列に関係する行だけが表示され、その列が強調される
- ブロックごとに行全体を色分けする
- 生成物はリポジトリにコミットしない
